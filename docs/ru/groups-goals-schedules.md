# Сессии, фоновые задания, цели, расписания и report/reply

Эта страница описывает, как в существующей группе выполняется работа:
чат-сессии, очередь ходов, фоновые задания `cs-job`, цикл целей,
cron-расписания и одноразовое окно отчёта между `main` и пиром. Сами глаголы
(аргументы, строки ошибок, кому они доступны) — в
[ctl-reference.md](ctl-reference.md). Эта страница объясняет, что они делают.

Пути вроде `daemon/goals.go` даны относительно корня репозитория. Каждое
утверждение называет функцию или константу, которую можно найти grep-ом.

## 1. Сессии

Группа (одна microVM, одно рабочее пространство) может держать несколько
независимых разговоров, называемых **сессиями**.

- **Сессия по умолчанию.** На проводе `""` означает сессию группы по
  умолчанию. `"-"` и `"default"` — её алиасы (`normalizeSession`,
  `daemon/sessions.go`).
- **Правило имени.** Любое другое имя должно соответствовать
  `^[A-Za-z0-9][A-Za-z0-9_-]{0,31}$` (`sessionNameRE`). Иначе ошибка —
  `invalid session name (must match [A-Za-z0-9][A-Za-z0-9_-]{0,31})`
  (`normalizeSession`).
- **Параллелизм.** Ходы выполняются по одному внутри сессии и параллельно
  между сессиями. Группа может выполнять не более `groupSlots = 10` ходов
  одновременно (`daemon/queue.go`).
- **Состояние сессии.** Каждая сессия хранит свой разговор. Гость закрепляет
  один claude session id на имя под `/workspace/.cs/sessions/<name>.id`
  (комментарий в `daemon/sessions.go`). Скрипт, делающий закрепление
  (`entrypoint.sh`), не отслеживается в этом репозитории, так что эта деталь
  здесь **не верифицирована**.
- **Реестр.** Хост держит список именованных сессий в
  `groups/<g>/.cs/sessions.json` (`sessionRegPath`).
  - Отправка в сессию добавляет её в список (`registerSession`).
  - Список вмещает не более `sessionRegMax = 256` имён. После этого новые
    имена не перечисляются, и демон логирует
    `session registry is full (256); "<name>" will not be listed`.
  - Реестр — рекомендательное UI-состояние. Настоящая запись — id-файлы
    гостя (комментарий над `sessionRegPath`).
- **Зарезервированный префикс `goal-`.** Любое имя, начинающееся с `goal-`,
  принадлежит циклу целей (`goalSessionPrefix`, `isReservedSession`). В эти
  сессии нельзя отправлять, и их нельзя очищать ни клиентам, ни ctl-плану:
  - ctl `send` в такую сессию падает с
    `ctl: session <s> is reserved for the goal loop` (`ctlDispatch`,
    `daemon/ctl.go`).
  - `job_done` и `notify`, нацеленные на зарезервированную сессию,
    доставляются вместо этого в сессию по умолчанию (`recordJobDone` в
    `daemon/notify.go`, ветка `notify` в `ctlDispatch`).

### Пределы очереди ходов (`daemon/queue.go`, `enqueue`)

Каждый ход проходит через `enqueue`: отправки оператора, срабатывания
расписаний, обратные вызовы заданий, ходы целей и отчёты.

- **Размер сообщения:** не более `sendMsgMax = 1 << 20` байт (1 МиБ).
  Сообщение больше падает с `message is <n> bytes; the limit is <max>`.
- **Байт в очереди на группу:** не более `sendQueuedBytesMax = 16 << 20`
  (16 МиБ). Сверх того:
  `group "<g>" already has <n> bytes queued (max <max>); retry later`.
- **Сообщений в очереди на сессию:** не более `sendQueueDepth = 64`. Сверх
  того: `group "<g>" send queue full (64 pending); retry later`.
- **Группа останавливается:** ошибка —
  `group "<g>" is stopping; retry once it is down`.
- **Заклинившая сессия:** если предыдущий ход сессии застрял и группа не
  смогла восстановиться, ошибка — `errSessionWedged`. Её текст начинается с
  `this conversation's previous turn is wedged and the group could not
  self-heal`.

## 2. Фоновые задания (`cs-job`)

`cs-job` — POSIX-шелл-скрипт, выполняющийся внутри гостя
(`sidecar/cs-job`). Он запускает команду в её собственной процессной сессии
(`setsid`), так что команда переживает конец хода. Демон только читает
состояние заданий и принимает обратные вызовы о завершении
(`daemon/jobs.go`, `daemon/notify.go`).

### Команды

Строка usage в скрипте перечисляет эти команды:

- **`run [--no-notify] -- <cmd...>`**
  - Печатает id задания и возвращается немедленно.
  - Обратные вызовы включены по умолчанию. `--no-notify` выключает их.
    `--notify` принимается, но ничего не делает.
  - Без команды падает с `cs-job run: no command`.
- **`spawn [--no-notify] <prompt...>`**: то же, что
  `run -- cs-subagent <prompt...>`. `cs-subagent` делает один LLM-вызов:
  печатает финальный ответ в stdout, а прогресс — в stderr
  (`sidecar/cs-subagent`).
- **`list`**: печатает колонки `ID STATUS RC SESSION CMD`. Команда
  обрезается до 80 байт.
- **`wait <id> [secs]`**: ждёт завершения задания. Бюджет по умолчанию —
  600 с. Он удаляет маркер `notify` задания, так что **ожидание отменяет
  обратный вызов**. По таймауту: `cs-job: wait timeout (<budget> s) — job
  <id> still running` (выход 1).
- **`status <id>`**: печатает статус задания. Файл статуса содержит
  `running` или `done`. Если файла статуса нет, печатается `unknown`.
- **`peek [-n N|-new] <id>`**: возвращается немедленно. Печатает строку
  заголовка `<id> <status> rc=<rc> bytes=<n> age=<s>s`, затем вывод:
  - По умолчанию — последние 40 строк.
  - С `-new` — только байты, добавленные после последнего peek. Смещение
    хранится в `<jobdir>/peek`.
  - В обоих случаях вывод ограничен `CS_PEEK_MAX` байтами (по умолчанию
    8000).
- **`logs <id>`**: печатает объединённые stdout и stderr задания.
- **`rm <id>`**: посылает SIGTERM группе процессов задания, ждёт примерно
  2 с (20 × 0.1 с), посылает SIGKILL, если оно всё ещё живо, затем удаляет
  каталог задания.
- **`clean`**: удаляет все каталоги заданий, кроме работающих и тех, чей
  обратный вызов ещё отправляется (маркер `notifying`).

### Правила и раскладка на диске

- **Id заданий.** Id — это basename-ы `mktemp`. Любой не-алфавитно-цифровой
  id отклоняется с `cs-job: invalid job id: <id>` (`chkid`). Проверка демона
  — `jobIDRE = ^[A-Za-z0-9]{1,32}$` (`daemon/jobs.go`).
- **Предел параллелизма.** Одновременно может работать не более
  `CS_MAX_JOBS` заданий (по умолчанию 8, `MAX=${CS_MAX_JOBS:-8}`). Сверх
  того: `cs-job: job cap reached (<n>/<max> running); wait or raise CS_MAX_JOBS`.
- **Каталог задания.** Каждое задание получает `/workspace/.cs/jobs/<id>/` с
  файлами `cmd`, `started`, `session`, `status`, `pgid`, `out` (stdout и
  stderr вместе), `rc` и маркерами `notify` / `notifying`.
- **Привязка к сессии.** Задание принадлежит сессии из `$KOTO_SESSION` на
  момент запуска или `default`, если переменная не задана.
- **Сироты.** Заголовок скрипта говорит, что задание, убитое перезапуском
  VM, позже перемаркируется в `orphaned` скриптом `entrypoint.sh`. Этого
  файла нет в репозитории, так что это **не верифицировано**.

### Обратный вызов о завершении

1. Когда команда выходит, задание выполняет `cs-job _notify <id>`. Это
   пишет строку `job_done` в `/workspace/.cs/ctl` с `id`, `rc`, `total`
   (размер вывода), `session` и base64 последних 1500 байт вывода.
2. Демон хранит не более `ctlMaxJobOut = 8 << 10` байт этого хвоста
   (`daemon/ctl.go`). Он записывает результат (`recordJobDone`) и сразу
   обновляет свой список заданий (`kickJobsRefresh`).
3. Результаты группируются по паре (группа, сессия). Таймер
   `notifyDebounce = 3s` перезапускается при каждом новом завершении
   (`armNotifyTimerLocked`, `daemon/notify.go`). Когда он срабатывает, все
   ожидающие результаты отправляются запустившей сессии как **один** ход.
   Этот ход начинается с `Background job(s) completed:` и цитирует каждый
   хвост с `> ` (`flushNotify`).
4. Если этот ход не удаётся поставить в очередь, повтор — через
   `notifyRetryDelay = 30s`.
5. Пределы буфера:
   - `notifyMaxPending = 64` результатов на ключ. Самые старые
     отбрасываются.
   - `notifyMaxKeysPerGroup = 32` ожидающих сессий на группу. Результаты для
     лишних сессий идут в сессию по умолчанию.

### Как хост видит задания

Хост не может смонтировать рабочее пространство гостя. Он читает состояние
заданий, выполняя маленький шелл-скрипт через гостевого агента
(`fcReadJobs`, `jobsListScript`).

- **Кеширование:** результаты кешируются на `jobsRefreshTTL = 3s`.
- **Сбои:** после неудачного чтения хост ждёт `jobsFailBackoff = 60s` перед
  новой попыткой. После `jobsFailWarnAfter = 3` сбоев подряд он логирует
  предупреждение.
- **Размер списка:** перечисляется не более `jobsMaxPerGroup = 256` заданий.
- **Логи:** `JobLogs` по умолчанию возвращает последние
  `jobLogsDefaultTail` байт (`fcJobLogs`). Пределы — в
  [protocol.md](protocol.md).

## 3. Цели (цикл целей)

Цель велит демону продолжать запускать ходы в группе, пока независимый
судья не примет критерии приёмки или пока не достигнут предел итераций.
Всё это — в `daemon/goals.go`.

### Создание цели (`goalSetBy`)

- **Обязательные поля:** группа, текст и критерии. Если одного не хватает,
  ошибка — `group is required`, `goal text is required` или
  `acceptance criteria are required`.
- **Предел размера:** текст и критерии ограничены каждый
  `goalTextMax = 16 << 10` байтами. Больший ввод отклоняется, а не
  усекается: `goal text is <n> bytes; the limit is <max>`.
- **Не на main:** цель на `main` отклоняется с
  `cannot set a goal on main`.
- **Предел итераций:** `max_iterations` со значением `<= 0` становится
  `goalDefaultMaxIter = 20`. Значения выше `goalMaxIterCeil = 200`
  понижаются до 200.
- **Предел активных целей:** группа может выполнять не более
  `goalMaxActive = 8` целей одновременно. Сверх того:
  `group "<g>" already has <n> active goals; finish or cancel one first`.
- **Старые записи:** установка новой цели удаляет завершённые записи целей
  группы (met, cancelled, exhausted).
- **Id:** id цели — 12 hex-символов (`newSchedID`, `goalIDLen`).
- **Персистентность:** цели сохраняются в `<state>/goals.json`
  (`GOALS_FILE`, `daemon/daemon.go`).

### Имена и сессии

Каждый запуск цели получает две собственные сессии, названные по **имени**
цели (`goalSessionSlug`). Старые записи без имени используют вместо него id.

- Работник выполняется в `goal-<name>` (`goalWorkSessionFor`).
- Судья выполняется в `goal-<name>-judge` (`goalJudgeSessionFor`).

Как выбирается имя (`resolveGoalNameLocked`):

- Если имя не задано, используется slug текста цели (`slugifyGoalName`).
- **Длина:** не более `goalNameMax = 16` символов. Иначе:
  `goal name must be at most 16 characters`.
- **Пригодность для сессии:** оба производных имени сессий должны проходить
  `sessionNameRE`. Иначе: `goal name "<n>" is not usable as a session name`.
- **Не должно выглядеть как id:** имя, соответствующее `goalIDRE` (12
  hex-символов), отклоняется. Ошибка начинается с
  `goal name "<n>" looks like a goal id`.
- **Коллизии:** если имя занято чат-сессией или сессиями другой цели, демон
  пробует `-2`, `-3` и так далее, подрезая основу, чтобы результат умещался
  в 16 символов. После `-99` он сдаётся с
  `could not find a free name near "<base>"`.

### Жизненный цикл

Статусы — это константы `goalStatus*`: `planning`, `awaiting_approval`,
`running`, `paused`, `met`, `cancelled` и `exhausted`. `met`, `cancelled` и
`exhausted` — финальные (`goalTerminal`).

1. **План (опционально, включён по умолчанию).**
   - С `plan` цель стартует в `planning`. Демон выполняет один плановый ход
     (`goalPlanPhase`, промпт `goalPlanMsg`) и переводит цель в
     `awaiting_approval`.
   - Он отправляет уведомление: `goal plan ready for review`.
   - **Кто может одобрить:** хостовый RPC `GoalApprove` или `goal_approve`
     ctl-плана. Ctl-план работает, только когда группа поставила цель сама
     себе (`ctlGoalSelfSet`). План, который main или оператор поставили
     группе, должен одобрить человек.
   - Когда main ставит цель с `plan:false` через ctl-план, она переводится
     в режим plan-first (`ctlDispatch`, см.
     [ctl-reference.md](ctl-reference.md)).
2. **Итерации.**
   - Каждая итерация в `running` увеличивает `Iteration`.
   - Она очищает контекст сессии работника (`clearGoalSession` →
     `clearSessionContext`). Транскрипт на хосте сохраняется.
   - Она отправляет промпт работника (`goalWorkerMsg`). Промпт включает:
     - каталог цели `/workspace/goal/<name>` (`goalDirFor`);
     - закрывающий отчёт предыдущего хода (`LastHandoff`, взятый из
       транскрипта функцией `goalCaptureHandoff` и обрезанный до
       **последних** `goalNoteMax = 4000` символов);
     - последнюю обратную связь судьи, если она есть (`LastFeedback`).
3. **Заявка (claim).** Работник заявляет о завершении, отправляя
   `goal_done`, пока его ход выполняется (`recordGoalDone`).
   - Заявки принимаются только во время хода цели. Иначе:
     `no goal turn in flight for "<g>"`.
   - Первая заявка побеждает.
   - Заявка без id принимается, только когда в группе открыт ровно один ход
     цели (`resolveGoalWindowLocked`).
4. **Судья.** Судья запускается только после заявки (`goalJudgeCheck`):
   - Его контекст очищается, и он получает `goalJudgeMsg`.
   - Он должен ответить через `goal_verdict`.
   - Ход судьи без вердикта повторяется один раз.
   - После `goalSilentJudgeMax = 3` заявок подряд без вердикта цель
     ставится на паузу с причиной `judge`.
   - Если вердикт «не достигнуто», причины сохраняются как `LastFeedback`,
     и цикл продолжается.
5. **Met** (`goalMarkMet`).
   - Статус становится `met`.
   - Отправляется уведомление `goal met`.
   - Ход `[koto] goal finished: ...` идёт в сессию группы **по умолчанию**,
     цитируя заметку работника (`goalInformCoordinatorMsg`).
6. **Exhausted** (`goalMarkExhausted`).
   - Когда `Iteration >= MaxIterations` и ничего не принято, цель
     завершается как `exhausted`. Она не ставится на паузу.
   - Отправляется уведомление высокой важности `goal exhausted`.
   - Ход `[koto] goal ended WITHOUT completing: ...` идёт в сессию по
     умолчанию (`goalCoordinatorExhaustedMsg`).

### Пауза, возобновление и отмена

- **Pause** (`goalPause`): только из `running`. Причина — `operator`.
- **Interrupt** (`goalInterrupt`): только из `running`. Ставит на паузу с
  причиной `interrupted` и также отменяет текущий ход работника.
- **Resume** (`goalResume`): только из `paused`. Цель возвращается к своему
  прежнему статусу (`running` или `planning`, если пауза была во время
  планирования).
- **Approve** (`goalApprove`): только из `awaiting_approval`. Цель
  становится `running`.
- **Cancel** (`goalCancel`): из любого нефинального статуса. Цель
  становится `cancelled`.

Паузы, которые демон применяет сам (`goalPauseWith`, `goalPauseOnStop`):

- **`stalled`:** сброс контекста, постановка в очередь или ход упали, либо
  ход так и не произвёл `turn_end`. Прежде чем сдаться, постановка в
  очередь повторяется `goalEnqueueRetries = 3` раза с интервалом
  `goalRetrySleep = 30s` (`goalEnqueue`).
- **`judge`:** см. шаг 4 выше.
- **`stopped`:** группа была остановлена. Уведомление гласит
  `goal paused (group stopped)`.

Поставленный в очередь ход цели, чья цель больше не в `running` или
`planning`, отбрасывается вместо выполнения (`goalTurnShouldRun`). Текст
ошибки — `goal turn skipped (goal no longer active)` (`daemon/queue.go`).

**Destroy:** уничтожение группы отменяет её цели и удаляет их записи
(`goalCancelOnDestroy`, `delGoalsFor`).

**Перезапуск демона:** цели в `running` или `planning` получают свои
драйверы обратно при старте демона (`resumeGoalDrivers`, вызывается из
`daemon/daemon.go`).

### Разрешение, какую цель имеет в виду глагол

Глаголы approve, pause, interrupt, resume и cancel принимают необязательное
имя (`resolveGoalLocked`). Имя совпадает либо с именем цели, либо с её id.
Если его опустить:

- при ровно одной возможной цели используется она;
- без цели: `group "<g>" has no goal`;
- при нескольких: `group "<g>" has <n> goals — name one of: ...`.

### Замечание о безопасности

Комментарий в начале `daemon/goals.go` говорит, что окно заявок защищает от
**случайностей, а не от злого умысла**. Все сессии группы делят один uid,
одно рабочее пространство и один ctl-FIFO, так что любой ход может записать
заявку. Используйте отдельные группы, когда разделение должно устоять
против враждебного агента.

## 4. Расписания (cron)

Расписания — в `daemon/schedules.go`, парсер — в `daemon/cron.go`.
Расписания сохраняются в `<state>/schedules.json` (`SCHED_FILE`) с режимом
`0600` (`saveSched`).

### Синтаксис cron (`parseCron`, `parseField`)

- **Пять полей:** минута `0-59`, час `0-23`, день месяца `1-31`, месяц
  `1-12`, день недели `0-6`.
  - День недели `7` вне диапазона.
  - Имена месяцев и дней недели не принимаются, потому что значения
    проходят через `strconv.Atoi`.
- **Алиасы** (`cronAliases`): `@yearly` / `@annually` → `0 0 1 1 *`,
  `@monthly` → `0 0 1 * *`, `@weekly` → `0 0 * * 0`, `@daily` /
  `@midnight` → `0 0 * * *` и `@hourly` → `0 * * * *`. `@reboot` нет.
- **Синтаксис поля:** `*`, `N`, `A-B`, списки через `,` и шаги через `/S`.
  - `S` должно быть между 1 и размером диапазона поля.
  - `N/S` означает «от N до максимума поля, каждые S».
- **День месяца и день недели:** если ограничены оба (ни одно не `*`), день
  подходит, когда совпадает **любое** из двух. Это классическое правило
  cron (`dateMatches`).
- **Часовой пояс:** локальный часовой пояс демона. `time.Now()` используется
  без явной зоны.
- **Строки ошибок:**
  - `cron: expected 5 fields, got <n> (...)`
  - `bad step "<s>" (must be 1..<n>)`
  - `range <a>-<b> out of bounds <lo>-<hi>`
  - Ошибки полей получают префикс: `minute: `, `hour: `, `day-of-month: `,
    `month: ` или `day-of-week: `.

### Пределы (`addSched`)

- **Обязательные поля:** `group is required`, `msg is required`.
- **Cron-выражение:** не более `schedCronMax = 256` байт.
- **Сообщение:** не более `schedMaxMsg = 16 << 10` байт.
  Сверх того: `msg too long (<n> bytes; max <max>)`.
- **На группу:** не более `schedMaxPerGroup = 100` расписаний.
  Сверх того: `schedule cap reached for <g> (100)`.
- **На весь демон:** не более `schedMaxTotal = 2000` расписаний.
  Сверх того: `daemon-wide schedule cap reached (2000)`.
- **Должно когда-нибудь сработать:** выражение без совпадения в ближайшие
  4 года отклоняется: `cron "<expr>" has no fire within 4 years` (`next`).
- **Id:** id расписания — 12 hex-символов (`newSchedID`).

### Срабатывание

- **Тайминг:** `cronLoop` просыпается на каждой минутной границе настенных
  часов и выполняет каждое включённое расписание, чей `NextDueAt` прошёл.
- **Куда идёт:** срабатывание ставит сообщение в очередь **сессии группы по
  умолчанию** (`fireSchedule` → `enqueueSend(it.Group, "", it.Msg)`). Оно
  испускает событие `sched_fired` или `sched_run`, когда запущено вручную
  через `sched run` (`runSchedNow`).
- **Без навёрстывания:** срабатывания, пропущенные пока демон был выключен,
  пропускаются. При загрузке `NextDueAt` пересчитывается от текущего
  времени (`loadSched`).
- **Отклонённое срабатывание:** если очередь группы отклоняет плановое
  срабатывание, расписание снова делается просроченным и повторяется на
  следующем тике (`rearmSchedule`). Ручной `sched run` не повторяется.
- **Нет будущего совпадения:** если у расписания больше нет совпадений, оно
  выключается (`Enabled = false`, `cronLoop`).
- **Плохие сохранённые записи:** запись в `schedules.json`, чей cron больше
  не парсится, отбрасывается при загрузке с предупреждением
  `load: drop <id> (bad cron ...)`.
- **Destroy:** уничтожение группы удаляет её расписания (`delSchedsFor`).

Кто может добавлять, перечислять или менять какие расписания — в
[ctl-reference.md](ctl-reference.md) §2.2.

## 5. Report/reply между main и пиром

Это `daemon/report.go`. Он позволяет `main` передать работу пиру и получить
**один** ответ обратно.

1. **Взведение.** `main` отправляет с `"reply":true` (ctl `send`). Демон
   ставит сообщение в очередь с дописанным `reportRequestNote`. Заметка
   говорит пиру, как отправить `report`. Тем же шагом демон взводит окно
   отчёта этой группы (`armReportAndEnqueue`).
   - Если постановка в очередь падает, ничего не взводится.
   - Повторная отправка при открытом окне заменяет его («последний
     побеждает»).
   - `from_session` выбирает, какая из сессий main получит отчёт.
     Невалидное или зарезервированное значение означает сессию main по
     умолчанию.
2. **Отчёт.** Пир пишет
   `{"cmd":"report","msg":"<base64>"}` в `/workspace/.cs/ctl` (ветка
   `report` в `ctlDispatch`).
   - Текст санируется и обрезается. Пустой результат падает с
     `ctl: report: empty message`.
   - Он урезается до `reportMsgMax = 4000` байт по границе UTF-8
     (`truncateRunes`). При урезании доставленный ход заканчивается на
     `(report clipped to 4000 bytes of <n>)`.
3. **Доставка.** `deliverReport` ставит в очередь main ход, начинающийся с
   `[report from <g>]`. Текст пира цитируется построчно с `> `
   (`reportQuoteBody`), за ним следует предупреждение, что содержимое
   написано пиром.
4. **Правила:**
   - **Один отчёт на взведение.**
     - Без открытого окна ошибка —
       `no reply pending: main must delegate with reply:true first (one report per delegation)`.
     - Пока отчёт уже доставляется, ошибка —
       `a report for this delegation is already being delivered (one report per delegation)`.
   - **Main перегружен.** Если очередь main отклоняет отчёт, окно
     открывается снова, и пир получает
     `main is backlogged, report not delivered — retry later: ...`.
   - **Истечение.** Окно истекает через `reportArmedMax = 24h` после
     взведения.
   - **Main не может отчитываться:** main получает
     `ctl: main has no delegator to report to`.
   - **Stop и destroy:** остановка или уничтожение пира закрывает его окно
     (`disarmReport` в `daemon/groups.go`).
