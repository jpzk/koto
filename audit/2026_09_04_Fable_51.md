## Threat model as built (verified)

```
tier 1  host user / operator            trusted by definition
   │  systemd unit: ProtectHome/ProtectSystem=strict/PrivateTmp, own userns
   ▼
tier 2  koto daemon (host process, operator uid)
        in-process: credential-injecting proxy (one loopback TCP port per group),
                    gRPC :8443 (mTLS + bearer + role ACL),
                    gVisor netstack gateway for network=wan|lan|full groups
        holds: OAuth token / API key / venice key, every workspace.img, the CA
   │  vsock only (proxy 9000, ctl 9002, gateway 9003, turn 9004, agent 10000)
   │  per-VM jail: userns + chroot + distinct uid + no_new_privs
   ▼
tier 3  one Firecracker microVM per group      UNTRUSTED (prompt-injectable)
        `main` = orchestrator: extra ctl verbs (spawn/send/stop/config_set/tail/list)
        peers  = self-scoped verbs only
```

Attackers considered: (a) a compromised guest, and separately a compromised `main`; (b) a non-admin gRPC client with a scoped role; (c) remote peers of a networked guest; (d) supply chain; (e) an unprivileged local user on the host who is not the operator.

## Headline

**The architecture holds where it matters most.** No path was found from a guest to the OAuth token, to another group's workspace, to the host filesystem, or to the operator's uid. The vsock plane authenticates groups by socket path and the jail binds only the group's own socket directory. The `[[marker]]` grammar cannot be forged from guest text. The ctl plane's main/peer split is enforced on every verb. The prior audit's three HIGH design findings that depended on shared filesystems (prompt.md self-injection, main puppeting peers through `/peers`, socket path traversal) are closed by the microVM runtime.

**What is open is narrower but real:**

1. A prompt-injected `main` can grant itself (or any peer) `network=full` through the ctl plane, and the proxy's L7 egress gate honors the change on the very next request, with no restart and no operator action. The default `network=none` posture is therefore only as strong as `main`'s prompt-injection resistance.
2. The L7 egress filter classifies the unspecified address (`0.0.0.0`, `::`) as public internet. A networked guest asking its proxy to `CONNECT 0.0.0.0:<port>` makes the daemon dial its own loopback. That reaches every other group's credential-injecting proxy port, every peer's published port, and any loopback-only service on the host. Chained with (1), `main` gets there with zero operator involvement.
3. Several guest-driven resource paths are unbounded and terminate in the daemon's own heap or the host disk (proxy request bodies, `job_done` buffering, schedules, the `[[bg]]` tailer, image uploads). The daemon is the process whose SIGTERM handler keeps every workspace image clean, so an OOM-kill here is a fleet-wide dirty-unmount event.
4. Two guest-controlled strings reach the operator's real terminal without passing any sanitizer: `RunScript` output and the group `model`/`effort` config values.
5. The wizard mints the default `koto ctl` identity as `admin`, while `CLAUDE.md` promises it is a least-privilege role.

Everything below is ranked by blast radius. Severity reflects impact under the trust model, not code-smell. "CONFIRMED" means the code path was read end to end and, where the claim rests on runtime behavior, that behavior was reproduced on this host.

## HIGH

### H1. `main` self-grants network egress live through the ctl plane (HIGH, CONFIRMED)

- **Where:** `daemon/ctl.go:267-282` (`config_set`: main-only, `req.Group` defaults to the caller, no refusal for `group == "main"`); `daemon/config.go:48-63` (`network` accepts `none|wan|lan|full` and the comment states "the proxy-side L7 gate flips live"); `daemon/proxy.go:520-527` (CONNECT / absolute-form → `serveEgress`) and `:945-961` (`groupNetwork(h.group)` re-read from `config.json` per request); guest side `fcguest/main.go:372` bridges `127.0.0.1:18888` → vsock 9000.
- **Attacker:** compromised `main`. Secondarily any peer once main has reconfigured it.
- **Scenario:** inside main, `echo '{"cmd":"config_set","network":"full"}' > /workspace/.cs/ctl`, then `HTTPS_PROXY=http://127.0.0.1:18888 curl https://<lan-or-tailnet-host>/`. `serveEgress` sees `full`, `egressTargetAllowed` passes LAN and WAN, `egressConnect` splices a raw tunnel. Only an info-level `[g] CONNECT …` line records it. The same verb also sets `root=yes`, `ports`, `size`, `autostart` on any peer, and main can stop + send (a restart) to make the NIC-level change take effect on a peer too. The documented contract that network changes "apply on `/restart`" is true for the L3 NIC and false for the L7 proxy path, which is enough for exfiltration and LAN pivoting.
- **Why this is HIGH and not "main is powerful by design":** the trust model's central promise is that `network=none` is the default and the proxy is the only egress. That promise is currently voidable by the tier-3 principal it exists to contain, silently.
- **Fix:** strip the posture keys (`network`, `root`, `ports`, `autostart`, arguably `size`) from what the ctl-plane `config_set` may set, leaving `model`/`effort`/`provider`. Independently, make the proxy's L7 profile a boot-time snapshot held in the handler, so raising it needs the same `/restart` that lowering it does not. On the gRPC side, document that the `config` verb is a posture verb, or split it.

### H2. L7 egress filter passes the unspecified address; the daemon dials its own loopback (HIGH, CONFIRMED)

- **Where:** `daemon/proxy.go:975-1021` (`egressTargetAllowed`): a literal IP is used as-is; `daemon/fcnet.go:160-187` (`fcClassifyDst`): checks loopback, link-local, self IPs, gateway subnet, private, multicast, broadcast, tailnet, else WAN. `grep IsUnspecified daemon/*.go` is empty. `daemon/proxy.go:1023-1033` (`egressConnect`) then `net.DialTimeout("tcp", "0.0.0.0:<port>")`.
- **Reproduced on this host:** a listener on `127.0.0.1:P` accepts a connect to `0.0.0.0:P`; a listener on `[::1]:P` accepts a connect to `[::]:P`. Linux delivers `connect()` to `INADDR_ANY`/`in6addr_any` locally.
- **Attacker:** any guest with `network` ∈ {`wan`,`lan`,`full`}; `main` can arrange that itself (H1). A DNS name whose A record is `0.0.0.0` takes the same path through `egressLookupIP`.
- **Scenario:** `curl -x http://127.0.0.1:18888 --proxytunnel http://0.0.0.0:8788/` (proxy ports are allocated sequentially from 8787, so they are guessable). The daemon dials loopback and splices. Impact:
  1. Cross-group proxy impersonation, the prior audit's finding #1, now reachable from inside a guest: requests go out with the operator's credential and are attributed to the victim group in `metrics.jsonl`, tok/s, activity phases. If the victim is a `venice` group, the attacker reaches the Venice key's authority.
  2. Peer groups' published ports (`KOTO_PORTS_BIND` defaults to `127.0.0.1`, `fc.go:754`): direct cross-group reach the ctl plane was designed to prevent.
  3. Any loopback-only host service (a `make dev` second daemon on 8444/9500, local databases, dev servers). The gRPC port is reachable but mTLS holds.
  4. Under `wan` it defeats "public internet only, host LAN blocked" at the most local address there is.
- **The frame-layer twin is not exploitable.** The Firecracker reviewer built a standalone repro against the vendored `gvisor-tap-vsock v0.8.8` + gvisor: a guest SYN to `0.0.0.0` returns `no route to host` and a SYN to `127.0.0.1` is dropped by the netstack. Only the L7 CONNECT path, which dials from the daemon process, is affected.
- **Fix:** in `fcClassifyDst`, return `fcDstCtl` when `ip.IsUnspecified()` (covers `0.0.0.0`, `::` and mapped forms). Belt and braces in `egressConnect`: refuse to dial any address that is unspecified or loopback regardless of the check result. Add tests for `0.0.0.0`, `::`, `[::]` and a stubbed resolver returning `0.0.0.0`.

## MEDIUM

### M1. Per-group proxy ports are unauthenticated loopback TCP: every local uid gets credentialed LLM access and a forward proxy (MEDIUM, CONFIRMED)

- **Where:** `daemon/proxy.go:831-843` (`net.Listen("tcp","127.0.0.1:<8787+n>")`, handler keyed by port only), `:520-598` (no inbound check; the `Bearer proxied` sentinel is replaced, never verified); `daemon/fc.go:874-881` (`fcSpliceToProxy` dials the same TCP port, so the handler cannot tell a vsock-originated connection from a local one); `daemon/daemon.go:168-172` (`BIND` default `127.0.0.1`).
- **Attacker:** (e) any local uid or process on the host; anyone with a loopback forward (SSH `-L`); and via H2, a networked guest.
- **Scenario:** `curl http://127.0.0.1:8787/v1/messages -d '{…}'` from any uid → the daemon injects the operator's OAuth token or API key and forwards; usage is metered as `main`. For a group with `network≠none`, `curl -x http://127.0.0.1:8788 https://192.168.1.10/` gets a CONNECT tunnel: the daemon is a LAN/WAN forward proxy for anyone local. In the container era this was reachable only on `koto-net`; with the daemon on the host it is every local uid, which the trust model does not list as trusted.
- **Fix:** bind the per-group listener to a unix socket under `run/fc/<g>.sock/` (parent dirs owner-only) and have `fcSpliceToProxy` dial that; or keep TCP but require a per-group random bearer minted at spawn, injected into the guest as `ANTHROPIC_API_KEY`, and verified before injection. Either also removes the guessable-port cross-group path in H2.

### M2. Proxy request bodies are buffered unbounded and connections are uncapped: guest-driven daemon OOM (MEDIUM, CONFIRMED)

- **Where:** `daemon/proxy.go:536-538` and `:711-714` (`io.ReadAll(r.Body)`, no `MaxBytesReader`; the only `MaxBytesReader` in the daemon is `claude_login.go`'s probe). The buffered body lives across up to 7 attempts with ≤30 s sleeps and a 600 s client timeout, and `injectThinkingDisplay` additionally unmarshals it into `map[string]any`. `http.Server` sets no `ReadTimeout`/`WriteTimeout`/connection cap; `groupSlots=10` caps turns, not proxy requests.
- **Attacker:** any guest (the LLM leg is always reachable, `network=none` included); any local user via M1.
- **Scenario:** 50 parallel `POST /v1/messages` streaming from `/dev/zero`. The guest's own 1 GiB preset is not the limit because it streams. The daemon holds 50 × N GiB. The `vms/` cgroup split protects the daemon from VM memory pressure but not from its own heap; an OOM-kill leaves every workspace.img dirty.
- **Fix:** `r.Body = http.MaxBytesReader(w, r.Body, 64<<20)` at the top of both LLM legs (Anthropic's own cap is 32 MB; return 413); a per-group in-flight semaphore (~16) around the upstream call; a write deadline for a guest that stops reading a streamed response.

### M3. The LLM leg is a path-, method- and header-agnostic authenticated relay to the whole upstream host (MEDIUM, CONFIRMED; endpoint impacts PLAUSIBLE)

- **Where:** `daemon/proxy.go:563` (`http.NewRequest(r.Method, upstream+r.URL.RequestURI(), …)`) and `:721` (Venice). Only `/v1/messages` gets the thinking rewrite and activity probe; everything else is forwarded verbatim with the credential injected and the response returned.
- **Attacker:** any guest; any local user via M1.
- **Impact (unverifiable offline, hence PLAUSIBLE):** with an API key, Files API uploads and Message Batches (spend that outlives the turn and the VM); with the OAuth token, whatever account/usage endpoints the Claude Code token authorizes; with Venice, `/api/v1/api_keys`. If `creds/venice.key` is admin-scoped, a guest can mint a fresh Venice key and read it back in the response body, which contradicts the design note that "a compromised Venice sidecar can talk to the proxy but cannot exfiltrate the key".
- **Fix:** allowlist `(method, path)` per provider. Anthropic: `POST /v1/messages`, `POST /v1/messages/count_tokens`, `GET /v1/models…`. Venice: `POST /api/v1/chat/completions`, `GET /api/v1/models`. Return 403 otherwise and log on the `llm` subsystem. Document that the Venice key must be inference-scoped.

### M4. `job_done` buffers unbounded guest-controlled memory in the daemon (MEDIUM, CONFIRMED)

- **Where:** `daemon/ctl.go:317-342` (decodes `req.Out` from base64 with no size cap; the only bound is the 1 MiB ctl frame ceiling in `fcframe.go:22`); `daemon/notify.go:64-93` (`recordJobDone` appends to `notifyPending[key]` and re-arms a 3 s debounce on every call).
- **Attacker:** any guest; the verb is self-attributed and open to all groups.
- **Scenario:** a stream of `{"cmd":"job_done","id":"<unique>","out":"<~1 MB>"}` lines. Dedup is by id, so distinct ids all accumulate, and every post re-arms the timer, so it never fires while the burst continues. `notifyPending` grows without bound. `notify` has a token bucket (`notifyAllow`) and a queue cap of 32; `job_done` has neither.
- **Fix:** truncate decoded `Out` in the handler (`cs-job` already trims to ~1500 B, so a few KB is harmless), cap the pending slice per key, and give `job_done` the same token bucket `notify` has.

### M5. No cap on schedule count or message size, on either plane (MEDIUM, CONFIRMED; prior #6 still open)

- **Where:** `daemon/ctl.go:577-603` (`sched_add`), `daemon/schedules.go:76-108` (`addSched` → `saveSched` rewrites `schedules.json` with `MarshalIndent` on every add); `daemon/grpc_server.go` `SchedAdd` has the same shape; `cronLoop` walks every entry each minute.
- **Attacker:** any guest (self-forced target does not limit count); any gRPC role with `sched_add`.
- **Scenario:** loop `sched_add` with `* * * * *` and a large `msg`. Disk growth of `schedules.json`, O(N) per-minute scan, and a queue (depth 64) that is always full.
- **Fix:** per-group schedule cap (the `ctlMaxSpawn` pattern) and a `msg` length cap in `addSched`.

### M6. The `[[bg]]` background-task tailer bypasses the disk-fill guards the turn sink has (MEDIUM, CONFIRMED)

- **Where:** `daemon/send.go:37-76` (`tailBackgroundTask`) → `daemon/proxy.go:246-253` (`streamLogAppend`, a bare `O_APPEND` write). Compare `fcTurnSink`/`turnWriter.write` (`fc.go:895-950`), which route the guest's one write channel into the host filesystem through a 1 MiB/s token bucket and a 1 GiB per-file ceiling, added after the fleet-wide EROFS incident.
- **Attacker:** any guest.
- **Scenario:** when claude backgrounds a Bash, the daemon parses the "Output is being written to: <path>" notice (`bgTaskRE`) and tails that guest file over `fcExecStream` into the same slot log via `streamLogAppend`, which has neither the bucket nor the ceiling. A guest can emit a synthetic tool result naming a fast-growing file, or simply produce large background output, and grow `groups/<g>/.cs/log.<n>` on the host bounded only by the 10-minute per-task timer and re-armable indefinitely.
- **Fix:** route the `[[bg]]` appends through `fcLogSinkWait` + `logSinkAppend`, keyed per group.

### M7. Jailed per-VM vsock sockets are `chmod 0666` inside `0755` directories (MEDIUM, CONFIRMED for dev clones; blocked by the `0750` state dir in installed mode)

- **Where:** `daemon/fcjail.go:101-121` (`fcJailFixupPerms` chmods every `v_<port>` listener in `run/fc/<g>.sock/` to `0666`); `daemon/fc.go:520` and `daemon/daemon.go:151` (`run/`, `run/fc/`, `<g>.sock/` all `0755`; confirmed `drwxr-xr-x` live in this clone).
- **Attacker:** (e) a local unprivileged user, when the parent path is traversable (a clone under a `0755` home, or any shared checkout).
- **Scenario:** `connect(2)` on a unix socket needs write permission on the inode, which `0666` grants everyone. `v_9002` is the ctl plane, authorized purely by which socket the connection arrived on (`fcCtlConn(g, c)` → `ctlDispatchPB("main", …)`), so connecting to `main`'s socket yields main's full verb set including H1. `v_9000` splices into that group's credential-injecting proxy. `v_9004` accepts forged transcript frames. Unjailed (`KOTO_FC_NOJAIL=1`) the sockets keep the daemon's umask and connect is denied. The mode FC gives its own `v` socket (the door to the unauthenticated guest agent on port 10000, which runs `exec` as guest root) was not verified.
- **Fix:** `chown` the listeners to the per-VM uid instead of `chmod 0666` (the VM uid is the only other principal that must connect), and create `run/` and `run/fc` `0700`. Verify FC's `v` socket mode.

### M8. `fcSelfIPs` is snapshotted once, lazily; addresses acquired later are not blocked (MEDIUM, CONFIRMED code; exploit PLAUSIBLE)

- **Where:** `daemon/fcnet.go:206-224` (`sync.Once` around `net.InterfaceAddrs()`, evaluated on the first frame classification).
- **Attacker:** a networked guest on a host whose addresses change.
- **Scenario:** the Firecracker reviewer's gvisor repro confirmed the netstack *will* `net.Dial` the host's routable primary IP and reach a service bound there, so the self-IP list is the only thing keeping a `lan`/`full` guest off cs_host's own listeners. Tailscale coming up after daemon start (CGNAT, classed LAN), a second NIC, a DHCP change, a VPN, or a container bridge created later are all absent from the set. Practical exposure needs a host service bound to a non-loopback address (koto's own defaults are loopback), so it is not a default-config break, but the documented invariant that `lan` cannot reach the koto host is only true for addresses present at the first guest frame.
- **Fix:** resolve self IPs per classification (`net.InterfaceAddrs()` is cheap) or on a short TTL; at minimum snapshot at daemon start, not at first guest frame.

### M9. Guest-controlled bytes reach the operator's real terminal unsanitized through two paths (MEDIUM, CONFIRMED)

The daemon has one sanitizer chokepoint (`daemon/sanitize.go` `sanitizeEvent`: SGR-only allowlist, drops C0/C1/OSC/DCS/cursor motion/bidi) applied to every `Event`, log line, and job stream. The TUI relies on it and adds only two bypass scrubbers (`sanitizeNotify` for the desktop OSC, `scrubVT` for the shell pane). `themeFrame` and `monoFrame` deliberately pass OSC and CSI through. Two strings reach the frame without any of the three:

- **M9a. `RunScript` output is raw by design, but the guest authors the bytes.** `daemon/grpc_server.go:665-672` ("Output is raw — the caller asked for this script's bytes, so no sanitizer"); `daemon/ctl_cli.go:494-516` writes chunks straight to the operator's tty; `tui/daemon.go:451-456` → `tui/view.go:1345-1362` renders them raw. The operator chooses the script; the guest, which with `root=yes` can persistently replace `/bin/sh` or `cat` through the `.rootovl` overlay, chooses the output. `JobTail` sanitizes the identical case (`grpc_server.go:501`). A guest emits `ESC]52;c;<b64>BEL` (clipboard write), `ESC]0;…` (retitle), or `ESC[?1000h` (mouse mode that persists after the pane) whenever the operator runs any script against it.
- **M9b. Group `model`/`effort` are unvalidated strings, settable by `main` on any peer.** `daemon/config.go:167-171` stores them through the generic `cfg[key] = v` branch (no allowlist, no length cap); reachable via ctl `config_set` (H1) and any gRPC role with `config`. They flow through `toPBGroupInfo` (`grpc_server.go:72-73`, no sanitize) into `WatchState`/`List` and render raw in the status bar (`tui/view.go:1810-1818`), the fleet MODEL column (`tui/top_view.go:334`) and the `/config` echo (`tui/model.go:3536`). Merely viewing the fleet writes a guest-chosen OSC to the operator's terminal, and it persists in `config.json`. The same gap covers `GoalItem.DoneNote`/`LastFeedback` (written by any guest via `goal_done`/`goal_verdict`, `ctl.go:439-442`, `goals.go:1201,1212`, rendered at `tui/model.go:2605-2610`) and `ScheduleItem.Msg` (any guest via `sched_add`, rendered by `/sched list`).
- **Fix:** sanitize `RunScript` chunks in the daemon by default with an explicit `raw` request flag for the binary case, and make `koto ctl runscript` scrub before writing to a tty. Run `sanitize()` in `toPBGroupInfo`, `toPBGoalItem`, `toPBScheduleItem` and the `config` response, the same one-chokepoint argument `sanitizeEvent` already makes. Validate `model`/`effort` in `applyConfig` (charset + length).

### M10. Image uploads accumulate on the host filesystem with no cap and no cleanup (MEDIUM, CONFIRMED)

- **Where:** `daemon/attachments.go:60-87` (`saveImage` writes `groups/<g>/.cs/uploads/img-<ns>.<ext>` on the host, per-file cap only); `daemon/fc.go:1080-1098` (`fcSendMsg` tars new uploads into the guest but never removes the host copy); the file is written before `enqueueSend` (`grpc_server.go:231-238`).
- **Attacker:** (b) any client whose role has `send`; the seeded least-privilege `agent` role has `send: "*"` (`pki.go:64-70`).
- **Scenario:** loop `Send{group, image: 4 MiB}`. Each call costs host disk regardless of queue backpressure. Host disk exhaustion is the documented fleet-wide failure (every guest remounts read-only). Every upload is also re-tarred into the guest on the next turn, so the workspace fills too.
- **Fix:** delete the host copy once the guest acknowledges the tar; cap `uploads/` per group and refuse beyond it; consider a per-role rate limit on `Send`.

### M11. The wizard mints the default `koto ctl` identity as `admin`, contradicting the documented least-privilege design (MEDIUM, CONFIRMED)

- **Where:** `daemon/setup_steps.go:133-137` (`pkiClient(sc.credsDir(), "agent", []string{"admin"})`); `daemon/ctl_cli.go:162` (`KOTO_CLIENT` defaults to `agent`); `daemon/pki.go:62-75` still seeds the `agent` role into `acl.json`, but nothing is bound to it. `CLAUDE.md` ("Trust model addendum: installed mode") says the opposite: the default CLI identity "cannot stop, destroy, reconfigure or run scripts". History: `fbb75a9` introduced the identity with role `agent` and the comment "Least privilege by default"; `60f3127` flipped it to `admin` and deleted the comment with no rationale.
- **Attacker:** (b) anything handed `koto ctl` with the default identity on the assumption it is read/converse-only: a coding agent, a CI job, a script.
- **Scenario:** the session can `runscript`, `shell`, `destroy`, `acl set`, all hardcoded admin-only verbs. The one identity meant to be scoped is a second superuser.
- **Fix:** revert to `[]string{"agent"}` and print the verb set in the handoff, or change the docs. Consider a non-admin default for `koto pki client` (`pki.go:361` defaults `-role admin`).

### M12. `make fetch` is not fail-closed and `make install` never re-verifies (MEDIUM, CONFIRMED; dormant until the first release)

- **Where:** `Makefile:177-205` (`fetch`: download, `chmod +x`, then `verify`); `Makefile:221-238` (`verify` and `require-artifacts`, the latter existence-only); `daemon/install.go:129-144` (`requireArtifacts`, existence-only) and `:189` (copies `os.Executable()` to `/usr/local/bin/koto` as root).
- **Attacker:** (c)/(d) whoever controls the dist host, a `KOTO_DIST_URL` mirror, or the network path (`curl -L` follows redirects; curl's default `--proto-redir` allows an https→http downgrade on redirect).
- **Scenario:** a tampered `koto` is served → `sha256sum -c` prints FAILED and `make fetch` exits 1, but the five executables stay in the tree → an operator or wrapper that re-runs "the next step" runs `make install` → the tampered daemon is installed root-owned and enabled. Dormant because `dist/artifacts.sha256` has no entries and `dist/VERSION` is `unreleased`. Contrast `build-firecracker.sh:123-132`, whose `FC_PREBUILT` path deletes on mismatch.
- **Fix:** download into a staging dir, verify there, `mv` into place only on success; make `install`/`require-artifacts` run `verify` whenever the manifest has entries; `koto install` refuses on mismatch; add `--proto '=https' --proto-redir '=https'` to the curl calls.

### M13. systemd unit: strong on the filesystem axis, open on devices, capabilities, address families and namespaces (MEDIUM, CONFIRMED as absent; directive compatibility PLAUSIBLE)

- **Where:** `daemon/install.go:486-547` (`renderUnit`). Present: `User=`, `ProtectHome=yes`, `ProtectSystem=strict`, `ReadWritePaths=<state>`, `PrivateTmp=yes`, `ProtectKernelTunables=yes`, `Delegate=yes`, `NoNewPrivileges=no` (justified: `newuidmap` file caps), `CPUQuota=`. Absent: `DevicePolicy=closed` + `DeviceAllow=/dev/kvm rw` + `DeviceAllow=/dev/vhost-vsock rw`; `CapabilityBoundingSet=CAP_SETUID CAP_SETGID`; `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_VSOCK`; `RestrictNamespaces=user mnt pid net ipc uts cgroup`; `ProtectKernelModules`, `ProtectKernelLogs`, `ProtectClock`, `ProtectHostname`, `LockPersonality`, `RestrictRealtime`, `SystemCallArchitectures=native`, `UMask=0027`.
- **Attacker:** tier 3 → tier 2 (a VMM escape into the daemon process) or (d) a malicious Go dependency. The unit is the last boundary before the operator's uid.
- **Scenario:** a compromised daemon opens `/dev/net/tun` or raw `AF_PACKET` sockets on the host LAN, or spawns arbitrary namespaces. None of that is needed by the daemon; the filesystem sandbox does not stop any of it.
- **Fix:** add the directives one at a time behind `TestRenderUnitIsValid` and a boot test with the jail, the `wan` gateway and `newuidmap` exercised (the three most likely to object). None was boot-tested in this audit.

### M14. The gVisor netstack runs inside the daemon process and is pinned to a 2024-09 snapshot (MEDIUM, CONFIRMED)

- **Where:** `daemon/fcnet.go:103-127` (`virtualnetwork.New` and `fcNetServe` in-process, one netstack per networked group); `daemon/go.mod:8,34` (`gvisor-tap-vsock v0.8.8`, which itself requires `gvisor.dev/gvisor v0.0.0-20240916094835`); upstream `gvisor-tap-vsock v0.8.9` was released 2026-05-11 and clears the six-week rule.
- **Attacker:** a networked guest (raw frames), and remote peers of one (response traffic).
- **Scenario:** every Ethernet frame a `wan|lan|full` guest emits is parsed by a userspace TCP/IP stack in the process that holds the OAuth token, every workspace image and the CA key. gvisor's netstack is memory-safe Go, so the realistic class is a panic or resource exhaustion rather than code execution, but an unrecovered panic in a netstack goroutine takes the daemon and the whole fleet down, and the pinned snapshot is two years of upstream netstack fixes behind. This is a design cost of the L3 profile that the docs do not name.
- **Fix:** bump `gvisor-tap-vsock` to 0.8.9 (and check whether it moves the gvisor pin); wrap `fcNetServe` in a recover that tears down only that group's gateway; long-term, consider running the gateway as a separate jailed process the way the VMM is, so a netstack fault is not a daemon fault.

## LOW

### L1. `sched_run` / `sched_del` / `sched_toggle` are verb-only on the gRPC plane (LOW, CONFIRMED)
`daemon/acl.go:236-274` (`targetOf` has no case for `SchedIDReq`/`SchedToggleReq`); `grpc_server.go:550-569`; `schedules.go:170-196` (`runSchedNow` → `enqueueSend(it.Group, …)`). A role scoped to one group can fire turns into, disable, or delete any group's schedules by id (ids are 48-bit random but appear on `sched_fired` events and in `sched_list`). The ctl plane has `ownsSched` (`ctl.go:622,635,648`); gRPC does not. Fix: resolve the schedule's group in the handler and re-run the target check.

### L2. `wan` guests can reach a real `192.168.127.0/24` (LOW, CONFIRMED)
`daemon/fcnet.go:174-176,196` classifies the whole gateway subnet as always-allowed, and the forwarder dials the destination verbatim on the host (`gvisor-tap-vsock@v0.8.8/pkg/services/forwarder/tcp.go:34`). Only `.1:53` is the gateway's own; every other address in the /24 goes out the host's default route. Matters only if the operator's LAN or a VPN uses that subnet. Fix: classify only `192.168.127.1` (and only :53 if strict) as `fcDstGW`; the rest is LAN.

### L3. Percent-encoded newline in the request path forges log lines (LOW, PLAUSIBLE)
`daemon/proxy.go:290-298` (`logProxyError` writes `[[err]] [koto-proxy] <decoded path> …` into the group log for every non-200 except 404) and `:513-517` (`llmFlowLog` → daemon log; `sanitize` keeps `\n`). A path containing `%0a` most likely 404s upstream, which mutes it; not confirmed which paths yield another status. `[[notify]]` and `[[turn_end]]` on the group stream are neutralized by `notifyExpected` and by turn completion riding the slot streams, so the residual is forged transcript furniture and forged daemon-log lines in `koto ctl logs`. Fix: `flattenInline` the path or log `r.URL.EscapedPath()`.

### L4. The guest chooses `TurnOpen.slot` with no check against the daemon-assigned slot (LOW, CONFIRMED)
`daemon/fcturn.go:35-42` bounds it to `[0, groupSlots)` only; the daemon told the guest its slot in `MsgReq.Slot` (`fc.go:1084`) but never checks it. A guest can open a turn stream on a slot owned by another of its own sessions and write `TurnEnd` into it, retiring that session's in-flight turn early or interleaving transcripts. Same trust principal, same VM, so integrity within a compromised group only. Fix: pin the expected slot per outstanding turn and reject a mismatched `TurnOpen`.

### L5. Long single lines: a 16 MiB tool frame becomes one log line held whole in RAM; the tailer's partial-line buffer has no independent cap (LOW, CONFIRMED)
`daemon/fcframe.go:21-22` (16 MiB guest frame), `fcturn.go:88-100` + `logparse.go:43` (`flattenInline` collapses newlines in tool name/input/err, no length cap), `logtail.go:337` (`buf += chunk[i:]` until `\n`). Bounded by the frame cap and the 1 MiB/s sink limiter, so churn rather than OOM, and a no-newline stream can grow the tailer buffer to the 1 GiB file ceiling. Fix: truncate marker bodies the way notify titles/messages are, and cap the partial buffer.

### L6. Client-cert identity and bearer-token identity are not bound to each other (LOW, CONFIRMED)
`daemon/auth.go:53-67` checks only that the leaf fingerprint is allowlisted; `:112-123` derives name and roles from the token alone. Any allowlisted cert plus a leaked admin token is admin, and revoking a device means remembering both `clients.allow` and `tokens.json`. Fix: require `tokens.json[cert CN].hash` to match the presented token (pki already sets `CommonName = name`).

### L7. `koto.env` is created world-readable for a moment, and a key folded into it outlives its revocation (LOW, CONFIRMED)
`daemon/install.go:581-598` (`sudo tee` creates with root's umask, then `chmod 0600`); `:427-428,450-458` (`writeEnvFile` copies `<state>/creds/anthropic-api-key` into it and preserves any existing value forever). `koto claude-login` renames the creds-dir key to `.disabled` (`claude_login.go:750-763`) but cannot touch `koto.env`, and `envAPIKey` outranks everything (`proxy.go:99,119-121`), so after the next restart the old key is sent again. The write race is narrow (only a fresh install onto a host that already has a key file). Fix: `sudo install -m 0600 /dev/stdin <path>`; stop copying the key into `koto.env` at all, since the proxy already reads it per request from the state dir.

### L8. `koto install -state DIR` renders the unit from `$KOTO_HOME`, not from `-state` (LOW, CONFIRMED)
`daemon/install.go:413` writes `KOTO_HOME=<o.stateDir>` into `koto.env`, but `:546,551` derive `WorkingDirectory=`, `Environment=HOME=` and `ReadWritePaths=` from the environment variable. A `make dev` shell (which exports `KOTO_HOME=<clone>/.dev`) followed by `make install` produces a unit whose sandbox points at a home-dir path `ProtectHome=yes` hides, with `koto.env` naming `/var/lib/koto`. Fix: thread `o.stateDir` into `renderUnit`; have the wizard and `koto tui` read the state dir from the unit's environment as `authInstalledStateDir` already does.

### L9. `seedStateDir` accepts a pre-existing state directory without checking ownership, mode or symlink (LOW, CONFIRMED; exploit PLAUSIBLE)
`daemon/install.go:259-268` (`os.Stat` then `MkdirAll`). Safe for the default `/var/lib/koto` (root-owned `/var/lib`), but `-state /tmp/koto` or `KOTO_HOME=/tmp/…` lets a local user pre-create the tree; the wizard then mints `ca.key`, `server.key`, `token-tui` (admin) and the OAuth credentials into a directory the attacker owns. Fix: require `Lstat` to be a real directory owned by `me.Uid` with no group/other write.

### L10. Install/uninstall/CLI hygiene (LOW, CONFIRMED)
- `purgeRefusal` (`uninstall.go:243-268`) accepts any dir with a `groups/` or `creds/` subdir and compares `$HOME` lexically without `EvalSymlinks`. Fix: require the `.koto-version` stamp, resolve symlinks.
- Upgrade re-merges the clone's `clients.allow` / `tokens.json` additively (`install.go:317-332`), resurrecting identities the operator revoked in the installed registry. Fix: merge only on first install, or print each identity added.
- `koto tui` falls back to exec'ing `<state>/koto-tui`, a daemon-writable path, when the TUI is not on `PATH` (`tui_cmd.go:37-48`); a compromised daemon plants a binary the operator later runs unconfined. Fix: drop the fallback.
- `koto ctl runscript` and `shell` write raw guest bytes to the tty (`ctl_cli.go:516,728`); `job-tail`, `ask` and `tail` are sanitized. Covered by M9a.
- `tools/tuiwalk/walk.py:160-170` runs an unpinned `fullstorydev/grpcurl:latest` with `creds/` mounted and the admin token on argv. Currently non-runnable (`make tui-walk` fails loudly). Fix: pin by digest or use `koto ctl`; mount only the four TUI files.

### L11. Guest-internal hardening (LOW, CONFIRMED; contained by KVM)
- `/workspace` is mounted with flags `0` (`fcguest/main.go:162`): no `MS_NOSUID|MS_NODEV`. Root-side ops (`writeWorkerFile` `:754-763`, `setupCS` `:185-213`, `overlayRootDirs` `:624-654`, `untarInto` `:658-674`) follow node-controlled symlinks under `/workspace` without `O_NOFOLLOW`. No node→guest-root primitive exists today because the content written is daemon-controlled, but it is one latent bug away for `root=no` groups. Fix: `MS_NOSUID|MS_NODEV` on the mount; `O_NOFOLLOW`/`lstat` on the fixed `.cs` control files.
- `sidecar/cs-notify:242-244` interpolates `$sev` and `sidecar/cs-job:113` interpolates `$sess` unescaped into the ctl JSON line; duplicate `cmd` keys are last-wins in the guest-side decoder. Only verbs the group's own identity already authorizes are reachable, so no privilege gain, but attribution can be forged. Fix: base64 or JSON-escape both fields.
- `fcguest/build-kernel.sh:241` fetches the guest kernel `.config` by tag URL over TLS with no checksum, while the kernel source commit is verified. A tampered config could re-enable vsock loopback (see I1). Fix: pin its sha256.

### L12. TUI local-file inputs (LOW, CONFIRMED)
`tui/theme.go:485` reads a drop-in theme SVG with no size cap; `tui/persist.go:37` restores `tui-state.json` `Draft` into the input bar unscrubbed. Both need write access to `run/tui` (owner/wheel). Fix: `io.LimitReader` on the theme read; scrub `Draft` on load.

## Checked and OK

Consolidated from all seven reviewers. Each item was read end to end.

**vsock plane and jail.** Group identity is the socket path: one dir per group (`run/fc/<g>.sock/v_<port>`), accept loop binds the group at listen time (`fc.go:565-594`), the jail bind-mounts only that group's sockdir (`fcjail.go`). No CID spoofing, no cross-group reach. Jail: `no_new_privs` before setgid/setuid/exec, gid before uid, empty env, all six namespaces plus cgroup, two-entry `uid_map`, per-VM uid `30000 + (port − PORT_BASE)`, only the group's own `workspace.img` + sockdir + ro binaries + `/dev/kvm` + `/dev/urandom` mounted. **ctl plane authorization.** `spawn`/`send`/`stop`/`list`/`resources`/`config_set`/`tail` refuse non-main (`ctl.go:143-315`). `sched_*` and `goal_*` force `req.Group = owner` for non-main; `sched_del/toggle/run` gate on `ownsSched`. `spawn` forces `main:false`, refuses the name `main`, validates `ctlGroupRE`, caps at `ctlMaxSpawn=100`. `destroy` is not a ctl verb at all. `report`'s one-shot window is race-free (`reportMu` held across arm+enqueue and consume; `disarmReport` on destroy). `notify` has a token bucket (burst 5, 1/15 s), flattened + truncated titles/messages (200/2000), queue cap 32. Session names normalized (`sessions.go:63-71`) and the charset contains no shell metacharacters, so the three guest-root shell-outs that splice one (`clearSessionContext`, `signalAgent`, `fcJobLogs`) are safe; job ids pass `jobIDRE`. `Spawn.main` has no privilege effect. **Proxy.** Client `authorization`/`x-api-key`/`host`/`content-length`/`transfer-encoding`/`connection` are dropped and the injected auth is `Set` after the copy loop (`proxy.go:458-466,578-583`); Venice leg strips every `anthropic-*` header. | M4 | fixed (memory); rate limiting **postponed** 2026-09-06 by the operator | `job_done` output truncated to an 8 KiB tail; pending results capped at 64 per (group, session). The heap growth the finding is about is closed. What remains is churn, and the audit's own prescription — "the same token bucket `notify` has" — is the WRONG fix: `notify`'s bucket is burst 5, refill 1/15 s, tuned for a banner where dropping is free. A `cs-subagent` fan-out of 20 jobs finishing together would have 15 completions silently dropped and the next token 15 s away, i.e. an agent never woken for work that really finished. Any bucket here must be ~30× looser (burst 64, refill ~2/s) so it flattens a loop without touching a real fan-out. **Two residual costs, traced 2026-09-06.** (1) `notifyMu` is a single GLOBAL mutex, so one group's loop adds latency to every other group's job traffic; `kickJobsRefresh` is guarded per group (`jobsRefreshing`), so execs are back-to-back but never fan out. (2) **NEW, not in the original finding: log-ring eviction.** Every `job_done` emits an unconditional info line into the global 200-line `logRing` (`logRingMax`, events.go) that `SubscribeLogs` replays and `koto ctl logs` reads. A guest looping the verb flushes every other group's recent daemon log out of the ring in under a second — evicting the forensic record an operator would reach for during exactly that incident. Neither existing cap touches it. Fix independent of any bucket: TTL-dedupe the log line the way flow logs are deduped (`llmFlowSeen`), which costs nothing and closes the eviction on its own. |
